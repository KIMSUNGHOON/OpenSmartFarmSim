# Thermal G1 publisher v1

Status: implemented synthetic software gate with pending production authorities. This contract applies only to the two-hour, self-authored [manifest-v2](../fixtures/manifest-v2.json) fixture and [thermal-v1](thermal-v1.md) aggregate model. It never grants real-source G0, local G2, crop or economics G3, or deployment G4 claims. The manifest's original `unresolved` list remains immutable; a separate signed release may clear only the two named implementation-review holds for exact bytes.

## Trusted inputs and review

`ThermalRunStore.put_snapshot` stores complete raw manifest, weather, and thermal fixture bytes under a tenant-scoped content ID, `thermal-snapshot-v1:` plus SHA-256 of a canonical JSON list of their three raw SHA-256 hashes. Its PostgreSQL rows check each raw hash and reject UPDATE or DELETE. Raw source files, rights, QC, URLs, fixture revision, null observation fields, applicability, and source-review limits are not replaced with a normalized copy. The server requires the published manifest-v2 SHA `c84e3774bcfaa8904d3d96a5d00876ade6b6890271c8f614ef5e5f20ca79566f` and its embedded byte-length and SHA pins for both fixture files. A submitted snapshot is storage only, never source approval.

A `collection_review` JobStore job binds exact canonical `thermal-g1-collection-review-input-v1` bytes: snapshot ID and all three raw hashes. Its completed publication must bind the same `thermal-g1-collection-review-proposal-v1` fields, a `proceed` decision, retained final-output and validation-report evidence, a successful matching invocation and capture, and exact `gpt-6-sol`/`xhigh` metadata. The publisher rechecks JobStore's private decision/receipt/capture verification against immutable rows and artifact bytes. `decision_at_utc` comes from the stored decision timestamp, never a caller-supplied instant. IDs supplied to `publish` only select tenant-scoped records.

JobStore launch/capture fields alone do **not** prove that an actual Codex CLI process ran: the current API can receive process ID, argv, JSONL and exit status from its caller. `execution_verifier` is a separate server-controlled authority that must attest that a trusted worker itself observed the spawned process, exact model and `model_reasoning_effort="xhigh"`, arguments, final output, JSONL and successful exit for the specific tenant, job, attempt, capture, snapshot and decision IDs. The publisher defaults to `REVIEW_HOLD` when this verifier is absent or returns anything other than literal `True`. Tests use an explicitly mocked verifier and cannot support an actual G1 claim. The production verifier and worker integration are pending.

## Release record

`release_resolver` is a server-owned source of canonical JSON bytes and an independent reviewer authority's signature. Neither publisher nor Run store holds that authority's signing key. Both require a separately configured `release_verifier(raw, signature)` to verify the authority signature and reviewer authorization with an independent public verification key and return exactly `authority_id`, `reviewer`, and immutable `review_evidence_raw` bytes. Both recompute the review evidence SHA-256 and compare it to the signed release. The publisher parses the evidence and requires its source/code/environment pins, reviewer, review time, `gpt-6-sol`/`xhigh` review method, and explicit operation-order, input-linkage and synthetic rights/QC outcomes to match the release. No request body, trace, manifest author declaration, or CLI proposal may supply an approval. Without this verifier, publication holds. The publisher requires `thermal-g1-release-v1`, synthetic-only scope, manifest/weather/thermal raw hashes, current code and schema digest, `backend/uv.lock` digest, reviewer different from the fixture author, review time after both fixture retrievals and no later than the decision, an external review-evidence SHA-256, source rights/QC/linkage verdict, and exactly:

1. `NO_ENGINE_OPERATION_ORDER_REVIEW`
2. `NO_SERVER_INPUT_LINKAGE_REVIEW`

The code digest hashes exact bytes of `thermal.py`, `thermal_units.py`, `thermal_publisher.py`, `thermal_run_store.py`, and `thermal-v1.schema.json`, then hashes their sorted canonical path/digest map. A code, lock, manifest, fixture or schema change requires new review and release bytes. Release evidence must substantiate independent binary64 operation-order, bounds, source-rights, and raw-pointer checks; a signed string or test fixture alone is not such a review. Current manifest v2 retains both hold labels to preserve its history. The release bytes are stored with each Run and authorize only their pinned snapshot and implementation; all other original holds remain.

## Server checks and accepted bytes

The publisher validates self-authored source rights and project QC against the pinned manifest; the NWS formula PDF's separate conditional disclaimer rights and unknown publication time remain explicit. It checks publication, availability and retrieval against the immutable decision time, null observation fields, hypothetical applicability, per-hour source IDs, manifest unit maps, JSON pointers into raw fixtures, and exact derived input-ID sets and rule versions. It then calculates two `candidate` traces from frozen bytes and demands exact replay. A separate formula path recomputes NWS saturation pressure, outdoor humidity ratio, interval solar power, 120 Euler steps, heater demand and delivery, vapor and energy ledgers, pressure, relative humidity, stability screens, and registered residual and half-step limits. These checks are software-contract evidence, not local physical accuracy.

The publisher changes trace 0's status to `accepted`, canonicalizes it, and hashes its **final raw bytes**. It then changes trace 1's status and reconstructs the temperature and humidity-ratio carry SHA and `basis_ref` from that final trace-0 SHA and actual last-state JSON pointers. Both final objects must pass Draft 2020-12 `thermal-v1.schema.json` with a date-time format checker. PostgreSQL stores both final raw byte sequences and hashes in one transaction and one immutable Run row. The row has exactly two ordered trace columns and checks status, Run identity, hashes and carry SHA; the server checks adjacency before insertion. A partial or candidate Run cannot commit. Conflicting Run IDs hold; identical publication is idempotent. Tenant-scoped reads revalidate hashes, signatures and carry. The signing keys, reviewer authority, execution verifier and `thermal_run_publish` database role must be separate from request principals and fixture authors.

The gate report binds tenant ID, Run ID, snapshot ID, review job/capture and decision IDs, decision time, manifest/code/environment digests, release digest, and both accepted trace digests. Its server-owned domain-separated signature covers canonical report bytes and ordered trace digests. The Run store compares the signed tenant to both the publication request and every later read. A returned receipt or stored trace is a synthetic G1 software-contract result only after genuine reviewer release and trusted worker verification. The test-suite mock signatures, fake CLI events, and test principal are structural evidence only and must never be published as real G1 evidence.

## Failure and remaining holds

Every missing or mismatched source pin, right, QC fact, reviewer, time, pointer, CLI proof, release, schema, equation, replay byte, or second-trace carry raises a coded hold before publication. A failed PostgreSQL insert rolls back the complete Run row. No partially accepted output is returned. Real-source G0, independent local measurements, future crop/economic validation, paired candidate comparisons and deployment proof remain held. This slice does not calculate crop growth, harvest, purchased energy, money, margin, or ranking.

The contract is exercised by [publisher tests](../backend/tests/test_thermal_publisher.py) and [PostgreSQL store tests](../backend/tests/test_thermal_run_store.py). The tests' HMAC signer/verifier is a test double and its arbitrary evidence SHA is not an independent review. A real server-owned release verifier backed by an external signing authority and immutable review evidence, trusted CLI worker proof, and separate non-owner database roles are required before using `publish` for an actual G1 Run.
