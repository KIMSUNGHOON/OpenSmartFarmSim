# Thermal G1 publisher v1

Status: implemented synthetic software publisher contract; actual G1 remains HOLD until trusted process, context, release, and database authorities are installed. This contract applies only to the two-hour self-authored [manifest-v2](../fixtures/manifest-v2.json) fixture and [thermal-v1](thermal-v1.md) aggregate model. It grants no real-source G0, local G2, crop/economics G3, or deployment G4 claim. The manifest original `unresolved` list is immutable; an independent release may clear only its two named software-review holds for exact pinned bytes.

## Trusted inputs and review

The [planning-event software candidate](planning-event-v1.md) now produces
immutable server-observed actual or explicitly hypothetical events and a public-key
DecisionContext verifier. Its test key/shared owner connection is not deployed
planning authority, and it does not clear execution, source or independent release
holds. Its exact implementation bytes are included in the code digest below.

`ThermalRunStore.put_snapshot` stores complete raw manifest, weather, and thermal fixture bytes under a tenant-scoped content ID, `thermal-snapshot-v1:` plus SHA-256 of a canonical JSON list of their three raw SHA-256 hashes. Its PostgreSQL rows check each raw hash and reject UPDATE or DELETE. Raw source files, rights, QC, URLs, fixture revision, null observation fields, applicability, and source-review limits are not replaced with a normalized copy. The server requires the published manifest-v2 SHA `c84e3774bcfaa8904d3d96a5d00876ade6b6890271c8f614ef5e5f20ca79566f` and its embedded byte-length and SHA pins for both fixture files. A submitted snapshot is storage only, never source approval.

A server-authorized `decision-context-v1` record is immutable and keyed by tenant, snapshot ID, and context ID. `decision_contexts` stores canonical signed bytes, raw SHA-256, authority ID, and a planning-event SHA-256. `context_verifier` must independently verify the authority signature and the planning event's exact D and actual/hypothetical kind; a caller-supplied historical timestamp is insufficient. The generic tenant/snapshot resolver can also serve market/API gates, which retain their own D-time availability rules. The thermal publisher additionally resolves the exact thermal snapshot bytes. Without the independent verifier, context creation, publication, and later reads HOLD.

A `collection_review` JobStore job binds exact canonical `thermal-g1-collection-review-input-v1` bytes: snapshot ID, three raw hashes, context SHA-256, context ID, exact D, `claim_mode`, and `decision_time_kind`. Its completed artifact must echo the same `thermal-g1-collection-review-proposal-v1` fields. The publisher checks the immutable job input, artifact, decision/receipt/capture/outcome, and exact `gpt-6-sol`/`xhigh` metadata against the signed context and pins. R (`review_at_utc`) comes only from the completed JobStore decision `recorded_at`; it never comes from a caller or CLI proposal. Context and snapshot rows must predate job submission; the verified capture must seal before R, and publication must follow R. `ThermalReviewContract` verifies the exact input against the immutable signed context and snapshot, maps the snapshot to the generic CLI decision candidate, and derives the required proposal bytes only after the generic server validator permits `proceed`. Its `authority_resolver` is a trusted server dependency; the test resolver and fake capture are not product authority or actual CLI evidence.

JobStore launch/capture fields alone do **not** prove that an actual Codex CLI process ran: the current API can receive process ID, argv, JSONL and exit status from its caller. `execution_verifier` is a separate server-controlled authority that must attest that a trusted worker itself observed the spawned process, exact model and `model_reasoning_effort="xhigh"`, arguments, final output, JSONL and successful exit for the specific tenant, job, attempt, capture, snapshot and decision IDs. The publisher defaults to `REVIEW_HOLD` when this verifier is absent or returns anything other than literal `True`. Tests use an explicitly mocked verifier and cannot support an actual G1 claim. The production verifier and worker integration are pending.

## Release record

`release_resolver` supplies canonical JSON bytes and an independent reviewer authority signature. Neither publisher nor Run store owns that authority key. `release_verifier(raw, signature)` must validate the authority and return immutable review evidence bytes plus a trusted release issuance time. Release and evidence both pin snapshot ID, context SHA-256 and quartet, source/code/environment hashes, reviewer, and the two named software holds. Review must follow retrieval of manifest, weather, thermal fixture and NWS law reference and the recorded issuance of the signed DecisionContext. The release authority must attest `reviewed_at_utc <= issued_at_utc <= R` with issuance no earlier than the context record; review need not precede D. An ex-ante D-time vintage/right claim additionally needs independent archived evidence for every adopted source, including the NWS law whose publication/availability is unresolved here. The software fixture cannot supply that proof by assertion. The release requires exactly:

1. `NO_ENGINE_OPERATION_ORDER_REVIEW`
2. `NO_SERVER_INPUT_LINKAGE_REVIEW`

The code digest hashes exact bytes of `thermal.py`, `thermal_units.py`, `thermal_publisher.py`, `thermal_run_store.py`, `thermal_review_contract.py`, `planning_events.py`, `planning_roles.py`, `planning_rpc.py`, `job_store.py`, `jobs.py`, `db.py`, `cli_contracts.py`, `cli_worker.py`, `cli_supervisor.py`, `cli_attestation_issuer.py`, `cli_ipc.py`, `cli_supervisor_service.py`, `cli_supervisor_client.py`, `runtime_roles.py`, `authority_rpc.py`, `runtime_login.py`, `content_access.py`, `execution_attestation.py`, `execution_verifier.py`, `thermal-v1.schema.json`, and `decision-v1.schema.json`, then hashes their sorted canonical path/digest map. A code, lock, manifest, fixture or schema change requires new review and release bytes. Release evidence must substantiate independent binary64 operation-order, bounds, source-rights, and raw-pointer checks; a signed string or test fixture alone is not such a review. Current manifest v2 retains both hold labels to preserve its history. The release bytes are stored with each Run and authorize only their pinned snapshot and implementation; all other original holds remain.

## Server checks and accepted bytes

The publisher checks self-authored synthetic rights/QC and pinned raw-byte provenance, including per-hour source IDs and exact unit maps. For every adopted manifest/source record it requires `published_at <= available_at <= retrieved_at <= R`; `ex_ante` also requires `available_at <= D` with immutable independent D-time vintage and rights proof. This v1 publisher has no durable, replayable proof packet for that claim and therefore always HOLDS `ex_ante` publication. `ex_post_replay` may use later material only with the explicit replay label and never asserts D-time knowledge. The NWS PDF's conditional rights and unknown publication/availability remain explicit. The server independently recomputes the NWS law, derived forcing, 120 Euler steps, ledgers, pressure/RH, residuals and registered bounds. Exact contextual D, R, mode, kind, context and review IDs enter candidate Run identity and byte replay. These checks establish only synthetic software behavior.

The publisher changes trace 0's status to `accepted`, canonicalizes it, and hashes its **final raw bytes**. It then changes trace 1's status and reconstructs the temperature and humidity-ratio carry SHA and `basis_ref` from that final trace-0 SHA and actual last-state JSON pointers. Both final objects must pass Draft 2020-12 `thermal-v1.schema.json` with a date-time format checker. PostgreSQL stores both final raw byte sequences and hashes in one transaction and one immutable Run row. The row has exactly two ordered trace columns and checks status, Run identity, hashes and carry SHA; the server checks adjacency before insertion. A partial or candidate Run cannot commit. Conflicting Run IDs hold; identical publication is idempotent. Tenant-scoped reads revalidate hashes, signatures and carry. The signing keys, reviewer authority, execution verifier and `thermal_run_publish` database role must be separate from request principals and fixture authors.

The signed gate report binds tenant, Run, snapshot, context ID/hash, exact D and R, claim mode, decision-time kind, review job/capture/decision IDs, source/code/environment/release digests, and both final accepted trace hashes. The Run store verifies the report and both traces against the independently signed context on insertion and read, recomputes contextual Run identity, and rejects tenant/snapshot/context swaps. PostgreSQL stores one immutable two-trace row and a composite tenant/snapshot/context link; the context table itself remains reusable by nonthermal snapshots. A returned receipt is structural software evidence only until real authorities and production role separation are demonstrated.

## Failure and remaining holds

Every missing or mismatched source pin, right, QC fact, reviewer, time, pointer, CLI proof, release, schema, equation, replay byte, or second-trace carry raises a coded hold before publication. A failed PostgreSQL insert rolls back the complete Run row. No partially accepted output is returned. Real-source G0, independent local measurements, future crop/economic validation, paired candidate comparisons and deployment proof remain held. This slice does not calculate crop growth, harvest, purchased energy, money, margin, or ranking.

The contract is exercised by [publisher tests](../backend/tests/test_thermal_publisher.py), [thermal review bridge tests](../backend/tests/test_thermal_review_contract.py), and [PostgreSQL store tests](../backend/tests/test_thermal_run_store.py). Their HMAC context/release signers, arbitrary planning-event hash, fake CLI capture, review authority and execution verifier are test doubles. Actual G1 remains HOLD without a real server-owned planning-event verifier, trusted CLI process/output sealing, an independently approved review authority and release, D-time evidence where required, and separate non-owner database roles.
