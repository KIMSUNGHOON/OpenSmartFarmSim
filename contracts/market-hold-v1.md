# Market unavailability report v1

Status: implemented as a synthetic software storage contract. Market source G0, actual thermal G1, API publication, and deployment G4 remain HOLD. This report says only that the market G0 review has **not been evaluated** for the specified decision. It does not claim that a source failed G0, that a crop is unsuitable, or that an approved MarketSnapshot exists.

## Authority and identity

`MarketHoldStore.issue_not_evaluated(tenant_id, input_snapshot_id, decision_context_id)` is a server operation. The request principal must have `market_hold_issue` for the tenant. The server independently reads a signed, immutable `decision-context-v1` through a service context reader and resolves the candidate IDs, sales period, and scope version through a trusted server callback. Neither a client ID nor CLI prose supplies the report verdict, scope, D, mode, or authority. The context reader must verify the planning event and signature as specified by [thermal-g1-publisher-v1](thermal-g1-publisher-v1.md); its `decision_context_read` privilege is separate from the request principal.

The canonical UTF-8 JSON report has `report_version=market-hold-v1`, an opaque `hold_report_id`, tenant, input snapshot ID, decision context ID and SHA-256, exact `decision_at_utc` (D), `claim_mode`, `decision_time_kind`, server `evaluated_at_utc`, `review_at_utc=null`, and a scope containing the candidate IDs, sales start/end UTC and `scope_version`. The only v1 status is `hold` with `evaluation_status=not_evaluated`; the fixed reason is `market_g0_not_evaluated`. The missing evidence names are market source rights, vintage, QC and an approved market snapshot. `reviewed_source_ids=[]` makes the absence of source review explicit. A future evaluated G0 decision needs a separate contract and new immutable record.

`install_market_hold_schema` runs as a schema owner after `install_thermal_run_schema`. PostgreSQL stores canonical raw bytes, raw SHA-256, a domain-separated HMAC, foreign keys to both the tenant's signed DecisionContext and an existing tenant-owned thermal input snapshot, and an intent SHA-256 of context hash plus scope. The unique tenant/intent key makes concurrent identical issuance idempotent; a changed scope version creates a new report. The trigger forbids UPDATE and DELETE. Reads recompute byte digest and HMAC and revalidate the signed DecisionContext, scope, and intent. Resolving a report for current use also rechecks that its scope equals the trusted server's current candidate/period/version scope. An older report remains available through the safe historical projection but cannot authorize the changed scope. Correcting a decision or report creates new immutable IDs. Signing keys and privileged DB roles must come from server configuration and stay out of request input, CLI output, repository, and logs.

## Read and display boundary

`resolve_market_context` accepts `{kind:"unavailable", hold_report_id}` only after a trusted repository checks the request tenant and exact D. For a signed report, the resolver uses the report's decision context ID and input snapshot ID to load the independently signed DecisionContext. It compares tenant, D, snapshot, context ID, claim mode, and actual/hypothetical kind. A caller may supply all four expected context fields for an additional equality check, but those fields are never authority; the signed context lookup remains mandatory. The market scenario and economic ledger can therefore resolve the same report without duplicating context fields in their request or baseline schemas. Older test fakes without context fields retain a legacy contract-only path and cannot stand in for the product's signed report store. This path never constructs `{kind:"available"}` or a MarketSnapshot.

The raw report is restricted. A tenant principal with `market_hold_context_read` can resolve its signed record. A tenant principal with `market_hold_read` receives only report ID, `hold`, reason codes and missing evidence via `get_public_report`; it cannot retrieve the scope, source material, raw bytes or signed context through that projection. The service reader verifies the context with separate credentials. At deployment, the request-facing database role must have no direct SELECT or INSERT on `market_hold_reports`, while the signing/verification service alone gets the narrow table grants it needs. The local PostgreSQL role test verifies request-role denial; actual deployment role wiring is a G4 requirement.

The report is distinct from a CLI job hold: a failed research, collection-review, or assessment invocation does not establish a market-source verdict. Even a valid `not_evaluated` market report keeps evidence-dependent scenario, margin, forecast and crop ranking claims on HOLD. A conditional scenario may use only explicit user-owned assumptions under the separate [market scenario contract](market-scenario-v1.schema.json) and cannot be presented as a sourced forecast.

## Verification boundary

[PostgreSQL tests](../backend/tests/test_market_hold_store.py) cover concurrent retry, a new scope version and rejection of its old report, tenant/context/D/mode substitution, an orphan signed context without input snapshot, immutable rows, owner-level byte tampering, API-safe projection and a request role without raw-table grants. The [joint scenario integration test](../backend/tests/test_market_signed_hold_integration.py) takes one synthetic signed DecisionContext and Market hold report through PostgreSQL candidate pinning and market/economic replay, then rejects a revoked read scope and changed report scope. They use a synthetic signing key and synthetic context verifier. Passing these tests proves the storage software path only; source rights/QC, a real signed planning event, service role configuration, API integration and production key management require independent evidence.
