# Decision evidence store v1

This contract covers durable storage wiring for a claimed job attempt. It does not certify a Codex CLI invocation, source rights, a gate result, crop performance, or deployment readiness. The synthetic test validator proves only that bytes, decisions, and publications are linked.

## Identities and closure

`claim` returns a server UUID `attempt_id`, numeric `attempt`, and a short lived lease token. The token is held only in the mutable current job row; immutable attempt history stores its SHA-256 for fencing late audit writes. A queued cancellation has no attempt. Each claimed attempt gets exactly one immutable `attempt_outcomes` row when it ends. `state` records queued retry, lease expiry/reclaim, success, hold, failure, or cancellation; `reason` records the cause. `decision_id` is nullable. A timeout, failure, cancellation, or expiry without validated output has no invented decision or output hash. A previously validated decision remains in restricted audit history if that attempt is later held, canceled, or expired. A retry receives a new attempt ID and cannot reuse the earlier decision for publication.

`claim(lease_seconds, allowed_stages=...)` validates a nonempty subset of known stages and applies that subset to expired-lease recovery and queued selection in one PostgreSQL transaction. The CLI worker must pass `research`, `collection_review`, and `assessment`; collection and simulation workers pass their own stages. An omitted allowlist preserves existing all-stage callers but is not an acceptable CLI worker call. The stage predicate is part of the locked queue query, so an older deterministic job cannot be claimed or recovered by a CLI-only worker.

For an AI stage, a live uncanceled lease may register one immutable `attempt_invocations` row before decision validation. It binds the tenant, job, attempt and attempt ID to the server verified job input SHA-256; retained prompt and output schema evidence IDs, their exact byte SHA-256 hashes and bounded version identifiers; `execution_kind`, CLI version, model, reasoning effort, and creation time. The referenced prompt and schema must belong to that attempt, be nonlate, have the required kinds, and pass a private byte read and hash check. The store rereads and rehashes both files before creating a decision and again before success or validated hold, including after restart. Withheld or corrupt prompt/schema bytes prevent completion; no digest is invented. The SQL decision trigger also requires the manifest for the same attempt.

For `codex_cli`, registration accepts only a `codex-cli N.N.N` version, model `gpt-6-sol`, and effort `xhigh`. These are worker reported fields in a storage record, **not proof that the CLI ran**. An explicitly constructed synthetic fixture store can instead register `execution_kind=synthetic_fixture`, `cli_version=synthetic_fixture`, and NULL model and effort. Normal stores default to denying that mode. The fixture mode establishes storage contracts only and cannot satisfy the runtime worker or any product gate.

The later server supervisor must call `record_cli_launch` after process spawn and `seal_cli_capture` after stream closure. One append-only launch row binds the invocation and attempt ID to retained, nonlate `launch_event` bytes, executable/version, argument-array SHA-256, prompt/schema hashes, observed process ID, and database spawn time. One append-only capture row binds that launch to the JSONL evidence ID, exact retained SHA-256 when permitted, final-output SHA-256, exit status, termination reason, usage parsed from the terminal JSONL event, and completion flag. The accepted JSONL stream is newline terminated with one `thread.started`, one `turn.started`, a completed `agent_message` item, and exactly one final `turn.completed`; the UTF-8 bytes of the last completed agent message must match the exact final output bytes. This follows the [official Codex SDK final-response selection](https://github.com/openai/codex/blob/main/sdk/typescript/src/thread.ts). The parser requires an item's update to follow its start, rejects updates after completion, and rejects non-null event errors or failed status. Malformed, duplicate-key, truncated, out-of-order, error-bearing, message-free, mismatched, missing, withheld, late, or corrupt bytes cannot authorize a decision. A withheld or never received JSONL evidence row stays linked to the capture and attempt outcome for audit without inventing a digest. A zero-exit complete capture and intact launch/JSONL bytes are required before a `codex_cli` decision and rechecked before success or validated hold. When a capture exists, the CLI outcome's exit status, termination reason, usage, and JSONL reference match it. If a failure has no sealed capture, exit status, usage, and process termination reason remain NULL; its separately recorded nonlate JSONL ID may still be linked for audit, without authorizing a decision. Lease-expiry recovery instead records the server closure reason with NULL exit status and usage; any sealed capture retains its separate process observations and JSONL reference. These rows are storage observations; a caller able to invoke these methods can fabricate them, so actual process execution, role separation, isolation, and credentials still require the later runtime and G4 tests.

The job transition, attempt closure, and any publication commit in one PostgreSQL transaction. Deferred SQL constraints require one closure per ended attempt. An active current attempt has no closure. A queued retry has a `queued` or `lease_expired` closure; cancellation while queued preserves it. Terminal jobs with an active final attempt require the matching outcome. `input_sha256_mismatch` may hold a queued retry without inventing another attempt or changing its earlier closure. Success requires the publication attempt and decision to match its outcome. Audit rows reject update and delete. An expired retryable lease is closed before the job is queued and claimed again. Late evidence may be retained for audit after expiry or cancellation, with `late=true`; it cannot authorize a decision or publication.

Each outcome may include a process `exit_code` (0–255), a bounded machine `termination_reason`, and a `usage` JSON object containing only nonnegative integer `input_tokens`, `output_tokens`, `total_tokens`, `cached_input_tokens`, `cache_write_input_tokens`, and `reasoning_output_tokens`. The `cache_write_input_tokens` key occurs in Codex CLI 0.157.1 JSONL and the [official SDK usage type](https://github.com/openai/codex/blob/main/sdk/typescript/src/events.ts). Omitted or unavailable counts and exit status remain NULL, never invented zeroes. Recovery writes `lease_expired`, `attempts_exhausted`, or `cancel_lease_expired` as the explicit termination reason and leaves usage and exit status NULL. Those codes are reserved for server transitions; a live worker cannot submit them through `fail`. A JSONL evidence ID, when supplied, must refer to nonlate JSONL evidence for the same tenant and attempt. A withheld JSONL row may be referenced with its explicit reason; its original digest is retained only when the authoritative policy permits, and otherwise remains NULL. If no JSONL row was recorded, the outcome reference is NULL. The evidence retention policy still decides whether exact bytes may be kept. Canceling a queued retry preserves the earlier attempt closure without creating another attempt.

## Exact bytes and access

`append_evidence` accepts `prompt`, `output_schema`, `final_output`, `jsonl`, `tool_event`, `launch_event`, and `validation_report`. SHA-256 and size describe exact retained bytes, with no normalization. A final output is at most 1 MiB; every other kind is at most 10 MiB. Each immutable row records tenant, job, attempt, kind, sequence, normal/late status, server classification, rights proof, policy version, and authorization snapshot ID. `receipt_state` is exactly `retained`, `received_but_withheld`, or `not_received`. Received but withheld bytes have no stored size or raw file; the exact original SHA-256 is kept only when the authoritative policy permits digest retention. Otherwise `hash_withheld_reason` explains its absence separately from the raw `withhold_reason`. Never received bytes have no digest. Withheld rows make no replay claim.

Caller `rights_ref`, `classification`, `source_id`, `intended_use`, and `access` are hints, not authority. The server owned resolver must verify immutable tenant/source/use authorization against the actual payload digest and return an authoritative source/proof ID, rights and policy versions, classification, read scope, and raw/digest retention permissions. Each evidence row links an immutable snapshot of that decision. Missing or failing authority is a G0 hold: raw and digest are withheld. The source resolver must inspect every source represented in combined bytes; this storage contract does not provide real G0 approval. Prompts, tool results, and final output may reproduce restricted source text, personal information, or credentials. Redacted derivatives need their own artifact and hash. No raw bytes, lease token, or secret enter metadata reads or public manifests. External reads require a server owned authenticated principal for the matching tenant: job/publication metadata needs `metadata`, private evidence bytes and stored original SHA-256 plus invocation/decision audit records need `auditor`, and full publication artifacts need `artifact`. The `metadata` evidence list omits the original hash, including when raw bytes were withheld but their digest was retained for audit. Caller supplied access strings cannot elevate scope. User cancellation needs `cancel`; worker acknowledgment uses the live lease token in `ack_cancel`. The API wiring and production identity provider remain a G4 hold.

Retained bytes use content addressed files under a tenant separated private directory. Directory opens refuse symlinks, directories are owned with mode 0700, and files are written with mode 0600. File and parent directories are synced before a database reference commits. Reads check size and SHA-256 again. A crash after file write but before database commit can leave a private orphan. This version does not perform garbage collection because reference safe cleanup requires a separate design.

## Decision and publication

`record_decision` accepts only final output bytes and proposed publication bytes and requires the current attempt manifest. It first retains the final bytes under policy, rereads and verifies them, then invokes the trusted server validator with those bytes and the current job input/stage context and proposed publication bytes. The canonical bounded report binds pass/code and validator version; tenant, job, attempt ID and stage; input and prompt/schema invocation versions, IDs, and hashes; execution identity; final output digest; and proposed publication artifact digest. A passing immutable validation receipt fixes the report hash, final/report evidence IDs, and these bindings. Failed validation, withheld final output, missing validator or manifest, canceled lease, wrong stage, or expired lease yields no decision. The SQL decision trigger requires a live uncanceled current attempt with no closure, retained matching evidence, and a passing matching receipt. At most one validated decision belongs to an attempt.

`publish` checks the current uncanceled lease, decision and proposed artifact digest, rereads and rehashes both private final and report bytes, strictly parses the canonical report, and compares every binding to the receipt, decision, invocation, and current job before and after its durable artifact write. Corruption or mismatch blocks publication. Deterministic collection and simulation jobs retain their no decision publication path. The public manifest contains server generated job, input, attempt, decision, and publication hashes, with no private final output bytes. A validated decision may still end in hold or cancellation with no publication.

The trusted validator returns an explicit `proceed` or `hold` disposition for `codex_cli`; only the explicitly enabled synthetic fixture mode may default a missing disposition to `proceed`. For `hold`, it must also return the exact authorized, normalized hold report bytes; a caller proposal that differs or lacks this trusted return cannot create a decision. The validator must establish underlying rights and gate facts before returning those bytes. The canonical validation report, immutable receipt, and AI decision bind the disposition and report SHA-256, and a CLI decision also binds the sealed capture ID and JSONL hash. `publish` accepts only `proceed`. A `hold` decision may call `finish_validated_hold` only while its matching lease is live and uncanceled. The proposed artifact and persisted report bytes must be identical, canonical JSON of at most 16 KiB with exactly `schema_version=hold_v1`, a bounded `reason_code`, and at most 50 distinct bounded `missing_evidence` identifiers. The server verifies the decision, receipt, final output, validation report, invocation input files, launch event, and JSONL before and after the private content write. One transaction then inserts an immutable tenant/job/attempt/decision/receipt linked `job_hold_reports` row, closes the job as `hold` with reason `ai_validated_hold`, and writes its attempt outcome. A deferred constraint requires this row for that reason and forbids a success publication for the hold decision. An operational failure, cancellation, or unvalidated hold may have an attempt outcome but no validated hold report.

`get_hold_report` returns only safe identifiers and timestamps to an authenticated same-tenant `metadata` principal. `read_hold_report` requires same-tenant `artifact` scope, checks the server-owned report authorization snapshot, and rereads the exact private bytes and SHA-256. It does not depend on a success publication. Hold reason identifiers are a storage envelope; their underlying source rights, missing-evidence applicability, and G0–G3 gates must still be checked by the trusted server validator. The bridge does not supply that validator or prove a process actually ran.

This store does not implement the actual `gpt-6-sol`/`xhigh` worker or independent G0–G4 checks. In the current fresh schema, the schema owner used by the trusted `JobStore` and validator has INSERT access to launch, capture, validation receipt, decision, hold, and publication tables; no production runtime role has yet been provisioned or verified. A role that can INSERT those rows can fabricate their authority, even if relational triggers accept them. The isolated PG16 test grants a sample runtime role `jobs` INSERT while denying direct INSERT into every authoritative bridge and outcome table; it proves only that sample grant set in its test schema. Production PostgreSQL 18 roles must enforce the same trust boundary, or an equivalent server signature must be verified, before deployment or G1 claims rely on CLI evidence. API authentication wiring, actual process observation, isolation, credentials, and independent signed release evidence remain G4 or G1 holds as appropriate. The future publisher's `execution_verifier(tenant, job_id, attempt, capture_id, snapshot_id, decision_id)` must verify exact observed argv, model, `xhigh`, JSONL, final output, and exit status against an independently signed release; this bridge provides identifiers and hashes, not that proof. G1 calculation/replay claims require their own evidence. The fresh schema installer does not migrate preexisting durable job tables; a production upgrade must preserve old rows as unverified audit history and must never synthesize validation evidence.
