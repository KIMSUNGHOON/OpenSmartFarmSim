# Synthetic thermal Run HTTP read v1

Status: internal G1 software read-path candidate. This contract applies only to a `synthetic-thermal-v1:<sha256>` Run previously accepted by the trusted `ThermalRunStore`. The [publisher contract](thermal-g1-publisher-v1.md) still requires real CLI execution attestation and independent release authority before actual G1 acceptance.

`GET /v1/runs/{run_id}` returns a bounded public summary: Run ID, `accepted` status, `synthetic=true`, `ex_post_replay` temporal provenance, decision/review and interval times, model/parameter/engine/unit versions, manifest SHA-256, two ordered trace SHA-256 values, and the number of 60-second points. `GET /v1/runs/{run_id}/series` returns that same Run ID and provenance plus ordered step-end points. Each point carries UTC end time, indoor temperature in K, humidity ratio in kg vapor per kg dry air, relative humidity as a fraction, modeled heat demand and delivered heat in W thermal, and delivered heat energy for that step in kWh thermal. These are model quantities, not purchased fuel/electricity or a crop forecast. The trusted Run store revalidates trace hashes, signatures and carry linkage; the API projection additionally checks accepted synthetic scope, source display rights, adjacency, units, finite numbers and the 60-second sequence before returning values.

All three read paths require the full publisher release fields bound to the Run's snapshot, manifest, code and environment hashes, including the two named software-review holds and synthetic source verdict. A storage-only signed test packet without these fields returns a generic `503` for every path; one path cannot display the Run while another cannot explain its provenance. This is a software consistency check, not independent proof that the release reviewer or CLI execution authority is real.

`GET /v1/runs/{run_id}/manifest` additionally requires `thermal_snapshot_read`. The server reloads the content-addressed snapshot, verifies its manifest/weather/thermal hashes against the signed release and gate, and returns only a typed display projection. `used_sources` includes the two synthetic fixture files actually used by the thermal Run, with locator, raw hash, vintage/revision, availability/retrieval times, null observation times, self-check QC, self-review and display right. `synthetic-economics-v1` is listed in `excluded_fixture_ids` because it is inventoried by the source manifest but not used by this thermal calculation. The NWS law reference has its official URL and pinned PDF hash, conditional display rights and terms, and explicit null publication/availability times. `source_unresolved_at_creation` preserves the immutable original manifest list, including the then-current `NO_ACCEPTED_THERMAL_RUN`; it is historical provenance, not the current gate verdict. Code, environment, release and trace digests are returned without signed bytes or restricted raw source data.

The tenant comes only from a trusted server principal. The principal needs `thermal_run_read`, and the manifest path additionally needs `thermal_snapshot_read`; `ThermalRunStore` independently checks the same tenant and revalidates bytes, signatures, DecisionContext and carry linkage. Missing/foreign Runs return `404`; malformed IDs return `422`; authentication and read-scope failures return `401`/`403`; integrity or store failures return a generic `503` without raw bytes. The response does not contain raw traces, signed gate/release bytes, keys, CLI prompts, or DecisionContext internals. The exact display projection is typed in `api_contracts.py` and exposed by OpenAPI 3.1.

This is a read path for an already accepted synthetic Run. The tests use a synthetic signing authority and do not establish actual CLI execution, independent release, real source G0, field G2, crop G3, full API orchestration, browser replay, or public deployment G4.
