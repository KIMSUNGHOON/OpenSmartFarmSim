## 1. One explicit app, one fixed resource

First slice: one additive `backend/app/api_supply_material_repeat.py` and its focused backend test. Public factory:

`create_repeat_material_app(*, directory: Path, access: ContentAccess, root_sha256: str, tenant_id: str, registry: BearerRegistry) -> PrincipalMiddleware`

Return the exact existing PrincipalMiddleware around an exact FastAPI instance. Operator configuration supplies an absolute owned artifact directory, exact ContentAccess, lower-case64 root hash, existing bounded tenant ID, and exact BearerRegistry. Configuration is not an HTTP input. Bind directory/path identity, access object/policy, root/tenant and reader function/code identities at assembly and compare request entry/after the actual read; changes deny release. No injected reader/provider, mutable caller map or serialized Handle grants authority. Reuse the existing HttpsApiService explicitly from the operator factory; do not add a listener/process/config framework or change default create_app/OpenAPI. Disable this app's docs/OpenAPI URLs so only the two data routes exist.

- `GET /v1/research/material-repeat/manifest` — operation `getRepeatMaterialManifest`.
- `GET /v1/research/material-repeat/frames/{index}` — operation `getRepeatMaterialFrame`.

The index path is exactly canonical decimal `0|[1-9][0-9]{0,2}`, with integer0..511; actual admitted frame length is enforced by the reader. Reject extra query pairs and every nonempty GET body; no arbitrary root/path/blob, ranges, listing, write/public-export or latest-root endpoint. A real but out-of-manifest index holds rather than selecting another frame. Request parsing/body completion is bounded by the same request deadline; an invalid or disconnected body never reaches artifact reading. Unknown route/method uses the same fixed error envelope (404/405).

## 2. Auth and source authority

Use existing BearerGrant/BearerRegistry/PrincipalMiddleware/current_principal only. Require the configured tenant and BOTH existing scopes `metadata` and `artifact`. These scopes authorize this operator-fixed research resource only; they are not a Farm ACL. Current principal is checked before any read, after actual read/normal FD cleanup, and again immediately before starting a successful ASGI response; expiry or changed tenant/scope suppresses bytes. Do not retain a pre-read principal as authority. Middleware keeps raw authorization out of the app and restores its ContextVar on every exit.

The operator must already be permitted to disclose/use/display this resource to that tenant. File group membership, Bearer authentication and synthetic-software acceptance do not manufacture source rights. Actual whole-source use/display checks remain required. `redistribute:false` is preserved: no public static assets, generic download/CAS server, all-rights exporter bypass, grant flip or raw data in reports. If this restricted same-tenant delivery is not already authorized, hold; a public alternative requires genuinely new own-authorized revisions and regeneration.

Each successful GET calls exactly one unchanged public [artifact reader](../backend/app/crop_supply_material_repeat_artifact_reader.py) entry: `read_repeat_material_manifest(directory,access,root_sha256)` or `read_repeat_material_frame(directory,access,root_sha256,index=index)`. Reuse the existing thread-pool pattern; never replace complete admission/reconstruction by root/metadata checks, raw filesystem reads, cached DTOs, an issued browser Root or a prior witness map. Its single original read60, all physical source/schema/rights/code/storage/saved-math fences and captured-OS FD cleanup remain intact. The reader's final source fence establishes currentness at that validation boundary. It is not an atomic guarantee against mutation after that boundary or a continuous Farm/DB revocation claim. Focused source faults occur during the actual reader and must reach its final guards; post-read HTTP checks separately retain config/code/policy and current auth. If a stronger atomic source-at-send requirement is needed, stop and version that boundary rather than pretending the public raw-byte API supplies it.

## 3. Bytes, errors and deadlines

Success is status200 with the EXACT returned bytes, `application/json`, `Cache-Control:no-store` and the existing middleware security headers. No JSON parse/reserialize, wrapper, compression middleware, custom numeric conversion, altered null/At/BigInt or content-disposition export. Require exact bytes type and size1..2097152 before success. Do not log body/raw token/hash, private path or restricted source identifiers.

Use existing closed ErrorEnvelope `{error:{code,message}}` with fixed messages, never raw Hold/exception details: 401 `unauthenticated` plus Bearer challenge; 403 `forbidden` for wrong tenant/scope/explicit permission denial; 422 `invalid_request` for syntax or `repeat_material_hold` for any RepeatArtifactHold (including actual index/source/rights rejection); 503 `repeat_material_unavailable` for other failures, output/type/code/config drift or elapsed request budget. Auth rejection takes precedence over a read failure. No error carries artifact bytes. Do not change global error models.

One monotonic adapter-success deadline is the first entry into the new FastAPI ASGI boundary+30seconds, AFTER the unchanged outer PrincipalMiddleware authenticates; it covers adapter parsing, queue/wait, actual read/cleanup and successful ASGI-start checks, and is never renewed between phases. It is not a whole-HTTP ingress deadline and does not account for prior outer authentication/transport. The existing HttpsApiService has no total-request ingress deadline to reuse (its keepalive/shutdown limits are different). Full client/TLS GET30, including outer authentication, transport and complete body reception, remains a separate mandatory actual acceptance and client timeout; it is not inferred from this adapter timer or raised/reset by this clarification. If that full path cannot satisfy30, delivery remains on hold. Do not trust client headers as a server ingress timestamp, replace/patch identity code, or claim a new service-level deadline. The unchanged reader operation still has its own original60 limit. A late read is not successful HTTP30 evidence: suppress its bytes after normal cleanup. The adapter cannot kill an in-process reader thread safely and must not abandon it as a validation lease. A client disconnect/cancel means no successful body release; an already running reader finishes or holds under its existing60 and closes its own resources, then its bytes are discarded. Test cleanup separately from client cancellation. Real successful manifest and selected-frame requests must each complete within30seconds; otherwise keep delivery acceptance on hold. Do not raise limits, reset meters, skip source checks or add cache/worker to force fit. Two GETs in one selection are not asserted to finish within a single30-second selection budget.
