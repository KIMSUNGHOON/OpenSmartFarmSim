## Synthetic time provenance correction

The raw [weather fixture](../fixtures/synthetic-weather-v1.json) has no `observed_start_utc` or `observed_end_utc` keys. Its [manifest v2](../fixtures/manifest-v2.json) entry declares both as JSON null. The raw [thermal parameter fixture](../fixtures/synthetic-thermal-parameters-v1.json) declares both as null in `law_source`, and its manifest v2 entry also declares both as null. The `2026-10-15T08:00:00Z` to `2026-10-15T10:00:00Z` interval is hypothetical applicability, split into two adjacent weather forcing intervals. Each synthetic trace source record requires both explicit null observations and separate required UTC applicability endpoints; timestamps in observation fields would falsely claim measurements. This correction stays within `thermal-v1` because no accepted trace exists to migrate.

The schema checks structure and fixed unit and rule literals; the server checks their immutable fixture links. Its single constant-forcing interval represents one weather hour, so the pinned two-hour fixture requires two adjacent traces in one run, with sequence indices 0 and 1. Each trace's weather source is scoped to its hour; a separate parameter source spans both. `original_unit` is a field-to-unit object: weather has `T_o=K`, `phi_o=1`, `p_o=Pa`, and `solar_interval_energy=J/m²`; thermal parameters have `temperature=K`, `humidity_ratio=kg_v/kg_da`, `heat=W_th`, and `time=s`. The deterministic source link must compare the complete object against that source's immutable manifest v2 `variable_units`, including a valid map attached to the wrong source. The humidity and solar derived results carry their distinct exact field-level ID sets from the corresponding interval in [synthetic-thermal-parameters-v1.json](../fixtures/synthetic-thermal-parameters-v1.json). Their registered rules are `thermal-outdoor-w-v1` and `thermal-solar-interval-v1`, both at `v1`, with `basis_ref` pointing to their respective `/conversion_rules/<name>` object in the raw-byte-pinned thermal fixture. The deterministic server compares each trace's rule ref, rule version, output version, basis, and per-hour input set with that registration; a shape-only rule label is insufficient. The second trace carries each derived state from the previous final step using a previous trace ID, complete raw-byte SHA-256, field-specific JSON pointer, and carry rule `thermal-state-carry-v1`/`v1`. Its `basis_ref` has the canonical form `trace-sha256:<raw previous trace SHA-256>#<last-step field pointer>` and `version=v1`; this project-specific basis names prior trace bytes and a field, not a measured source. The deterministic server must derive the hash and pointer from the prior raw trace and require exact equality with `basis_ref`, `previous_trace_sha256`, and `previous_state_pointer`; arbitrary self-declared basis text cannot establish a carry. A source-labeled assumed value cannot replace it. The server must also establish calendar-valid UTC ordering, per-trace source and step containment, adjacent intervals and consecutive indices, raw manifest and fixture pins, JSON-pointer resolution, exact per-hour derived input sets, prior trace identity and final-state equality, and publication/availability/retrieval chronology. It must reject missing, extra, swapped, and cross-hour references and hold when proof is unavailable. The test-only reference checkers in [test_thermal_contract.py](../backend/tests/test_thermal_contract.py) exercise these obligations with shape sentinels, but issue no gate decision or engine calculation. No trace has been accepted or published, so `thermal-v1` remains the proposed version. ## Synthetic inputs and upstream numerical bounds

The fixture explicitly assumes `C_eff=1,000,000 J/K`, `M_da=1,000 kg_da`, `V=850 m³`, `K_env=200 W/K`, `A_floor=100 m²`, `f_abs=0.5`, `F=0.02 kg_da/s`, `E_canopy=1e-5 kg_v/s`, `Q_ground=0 W`, initial `T=293 K`, `w=0.008 kg_v/kg_da`, and an available indirect sensible heater with `500 W_th` cap and `293 K` setpoint. Rounded `R_da=287 J/(kg_da*K)`, `R_v=461 J/(kg_v*K)`, `c_da=1000 J/(kg_da*K)`, and `lambda=2,500,000 J/kg_v` are assumptions, not site measurements or adopted literature properties. Every scalar including zero has an origin, basis, unit, and version. The first 3,600 s hypothetical weather interval is 290 K, 50% RH, 100,000 Pa, and 3,600 J/m² solar; the second is 289 K, 60% RH, 100,000 Pa, and zero solar. Their raw bytes remain pinned in manifest v1 and v2.

The versioned `thermal-outdoor-w-v1` conversion first applies the Kelvin-to-Celsius offset and hPa-to-Pa factor, then `e_o=phi_o*p_sat_Pa` and `w_o=(R_da/R_v)*e_o/(p_o-e_o)`. Its immutable input IDs include the saturation rule and all weather fields. `thermal-solar-interval-v1` divides interval solar energy by the linked duration and multiplies by area and absorbed fraction. Neither conversion copies or alters the weather file. At 289, 290, and 293 K the registered NWS expression yields about 1801.45933, 1919.93679, and 2317.30640 Pa, respectively; it is monotone across the selected range. The outdoor humidity ratios are 0.006034303321 for the first 290 K interval and 0.006802623257 kg_v/kg_da for the second 289 K interval.

With the fixed heater cap active throughout the upstream envelope, the equilibrium temperatures are `292.386363636 K` and `291.159090909 K`; humidity equilibria are `0.006534303321` and `0.007302623257 kg_v/kg_da`. This is only a bulk synthetic undersaturation bound; no cover/screen surface temperature is modeled.
