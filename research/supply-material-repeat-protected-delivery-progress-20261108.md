# 반복 material 보호 전달 — backend 구현의 중간 진행

[strict client 라이브러리](supply-material-repeat-client-library-20261108.md) 뒤에 고정 root의 manifest/Frame GET을 구현했다. [원문·출처·검사 범위](artifacts/supply-material-repeat-protected-delivery-progress-20261108.json)는 **서로 다른4개 ASGI 소프트웨어 검사/3개 유한 guard**다. 전체 보호 전달의 수용이나 한 명령의4개 통과가 아니다.

실제 first13 합성 artifact의 원 manifest, 같은 At/다른 basis의 Frame0/1·dense null/confirmed를 원 물리 bytes/hash/길이와 대사했다. 하나의 불변 registry에서 인증/테넌트/각 scope 거부9행은 추가 public reader 진입0, 입력·메서드/경로 오류10행도 진입0이었다. admitted index2는 실제 전체 재구성 뒤422로 보류했고 정상 Frame 재시도를 확인했다.9/10행은 별도 pytest 개수나 모든 metadata I/O0이 아니다. fixture setup은 실제 수치/게시 작업을 포함한다.

원 reader60과 전체 source/권리/code/storage 검증은 유지했다. 새 adapter30은 기존 외부 인증을 거친 FastAPI 진입부터 시작하며 전체 HTTP30의 증거가 아니다. 콜 시간은 여러 실제 읽기·inventory·assertion을 포함하므로 단일 HTTP 지연으로 사용하지 않는다. scheme=https의 직접 ASGI이며 이 기록은 실제 TLS/전체 client GET30·경과시간 expiry·running-reader 취소/연결 종료·source/policy drift 수용을 포함하지 않는다.

[전달 계약](../contracts/supply-material-repeat-protected-delivery-v1.md)은 구현 전 동결한 규범 제안 판본을 그대로 보존했다. 그 문두의 당시 pending/no-implementation 상태와 현재 구현 진행을 구별하며, 규범을 바꾸거나 과거 검사 지문을 새 판본으로 재명명하지 않는다. 전체 전달 구현·수용은 여전히 보류다. 현재 테스트 파일에 뒤에 붙은 시험은 이4개 결과로 실행했다고 세지 않는다.

이후 후속 TLS/expiry 두 case를 함께 실행한 명령은 TLS의 최종 자식 FD 정확 일치 검사에서5 대6으로 실패했다. 최종 TLS metrics와 그 뒤 inventory/source 확인은 도달하지 못했고 원인도 아직 확인하지 않았다. 같은 명령의 별도 expiry case는 실제 읽기의 정상 반환·FD 정리 뒤 두 경계의 인증 재검사를 통과했다. 이는 registry가 지원하는 UTC clock 값의 제어이며 실제 경과시간/TLS expiry가 아니다. 이 mixed 결과를 앞선4개 checkpoint의 통과 수에 합치지 않는다. checkpoint QA는 앞선4개를 보존한 판본이며, 뒤에 붙은 TLS/expiry 작업 사본을 통과 suite로 게시하지 않는다.

후속은 실제 경과 expiry/source/code/policy 변경·running-reader ownership, 검증된 TLS·전체 GET30 및 raw TS transport/동일 출처 proxy다. 첫2Frame 결과를 선택 예정인 full14/10Frame에 외삽하지 않고, 비공개 기존 full artifact의 실제 전달을 따로 확인한 뒤 같은 선택의 metric3D/표·그래프/브라우저로 진행한다. use/display=true·redistribute=false, 원 모델/자료·이전 수집 HOLD/feature RED를 보존하며 public raw/token 복사를 만들지 않았다. Farm/작기/비용·G0–G4/R2·hosted CI·전체 client/goal은 미수용·미완료다.
