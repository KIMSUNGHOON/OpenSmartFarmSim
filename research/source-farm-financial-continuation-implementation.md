## Response observation and failed attempts

The SDK reads each bounded stream and then cancels/releases its reader. In
actual Chromium, using `Response.finished()` stalled; `requestfinished` was
absent and `requestfailed` also reported otherwise successfully consumed
responses. Those runs failed and are not acceptance evidence. A minimal probe
reproduced this with a drained stream followed by cancel/release and reload.

The [test-only observer](../web/e2e/observe-api-body.mjs) is installed before
the application's fetch capture and again on reload. It returns the original
Response and read bytes, observing only the actual reader EOF. It records path,
method, status, cache policy and monotonic durations, without response bodies,
request headers or credentials. All observed completions must exactly match
the actual request multiset and all required endpoints; unread or failed bodies
cannot satisfy that check. The SDK's existing 30-second deadline is unchanged.
A focused real Chromium probe verified unchanged UTF-8 bytes, reload coverage,
unread-body refusal and aborted-body refusal (four checks).

An earlier harness mutation of an assembled assessment dependency correctly
produced `owned_cli_binding_hold`; the financial assessment now uses a newly
assembled coherent service. A small subprocess probe also showed that a final
phase line plus a final report could lose the report when mixing buffered
`readline()` with `communicate()`. The redundant phase line was removed; the
single final report verifies the recovered Run. One owned run was interrupted
before this correction, and its cleanup completed. None of these failed or
interrupted attempts count as passing cases.
