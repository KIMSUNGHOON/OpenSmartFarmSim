# 작성 농장 입력 → 저장 Run 합성 연결 시험

2026-09-30. [시험](../backend/tests/test_authored_full_software_path.py)은 실제
PostgreSQL 16.15의 별도 SCRAM 로그인과 작성 농장 등록 서비스를 사용한다. 사용자
소유로 선언한 합성 입력을 등록하고, 검토 작업을 임대한 가짜 CLI가 완료한 뒤
저장된 CLI 캡처와 합성 관찰자 서명을 실제 완료 검증기로 검사했다. 완성된 증명에
대응하는 120시점 계산 후보도 실제 작성 입력에서 한 번 도출해 해시를 대사했다.

그 뒤 별도의 **합성** 검토자 키로 보고서 세 개를 서명하고 실제 해제 검증기와
불변 저장소에 넣었다. 실제 `AuthoredRunPreparer`, `AuthoredSimulationService`,
`AuthoredSimulationWorker`, `AuthoredRunStore`를 연결해 한 작업에서 원자적으로
Run을 게시했다. 재조회에서 검토 작업·해제 해시, 두 개의 연속된 60시점 궤적,
완료 상태, 다른 테넌트의 읽기 거부를 확인했다.

시험 시간의 중복 재계산을 제한하려고, 처음 실제 검증을 통과한 완료 증명과
계산 후보는 후속 서비스 조립 동안 같은 불변 객체로 고정했다. 따라서 이 시험은
후속 호출마다 권리·자료를 재검사하는 동작의 단독 증거가 아니다. 각 서비스의
별도 시험이 변경/철회와 원자 롤백을 다룬다.

격리된 로컬 PostgreSQL 16.15를 `OSSF_TEST_PG_DSN`으로 지정하고 `backend/`에서
다음 명령을 실행했다.

```bash
uv run --locked --group dev pytest -q --tb=short tests/test_authored_full_software_path.py
```

결과: **1 passed in 230.07s**. 변경된 합성 서명 도우미의 순수 시험은
`uv run --locked --group dev pytest -q tests/test_farm_authored_release.py`로
**1 passed in 0.44s**. 이 실행의 임시 소켓 경로는 재현용 고정 설정이 아니며,
다른 환경은 자체 `OSSF_TEST_PG_DSN`을 지정해야 한다.

## 실제 HTTPS·브라우저 재생 확장 (2026-09-30)

같은 서비스 체인의 최종 Run을 별도 모의 응답으로 바꾸지 않고 표준
`ApiRuntime`에 조립했다. 브라우저는 인증 후 **작성 농장 실행** 화면에서
등록된 `farm-1/r1`을 조회하고, 서버가 재검사한 등록 해시를 확인한 다음
**3D 열 재생** 화면에서 완료 작업 ID로 동일 저장 Run을 열었다. 실제 HTTPS
요청 4개(작성 판본 요약, 작업의 Run, Run 요약, 120시점 열 자료)는 모두
200이었다. Chromium은 최초·최종 시각의 장면·그래프·요약·표 숫자를 서버
투영 결과와 대조했고 콘솔 오류는 0개였다. [실제 시험 캡처](artifacts/authored-full-chain-scene.png)는
이 합성 Run의 3D 장면과 같은 시각의 수치다.

실행: 위와 같은 격리된 PostgreSQL 16.15/SCRAM 환경에서
`uv run --locked --group dev pytest -q -s --tb=short tests/test_authored_full_software_path.py`.
결과: **1 passed in 237.23s**. 첫 브라우저 확장에서 검토 증명 객체가
새 API 작업 저장소가 아닌 기존 서비스를 참조해 런타임 조립이 거부됐다.
같은 작성·검토·작업 저장소로 결속해 해결했다. 다음 실행에서는 시장
보류의 원래 서버 범위 해석기가 HTTPS 조립에 없어 작성 판본 조회가
422로 보류됐다. 원 등록과 동일한 범위 해석기를 전달한 뒤 위 검증이
통과했다. 이 실패들은 근거 재검사 경계가 작동한 증거이며, 보류를
우회하거나 새 시장 자료를 만든 결과가 아니다.

## 브라우저의 완료 작업 재접수 확장 (2026-09-30)

같은 실제 PostgreSQL/SCRAM, 표준 HTTPS API, Chromium 경로에서 이미 완료한
검토·열 계산 작업을 화면 버튼으로 **원래 멱등 키로 재접수**했다. 등록 판본
조회 1개, 검토 POST 202와 작업 상태 GET, 계산 POST 202와 작업 상태 GET,
작업의 저장 Run GET, Run 요약 GET, 120시점 자료 GET까지 실제 HTTPS 응답
8개를 확인했다. 브라우저의 장면·그래프·표가 같은 저장 Run을 가리키며 콘솔
오류는 0개였다. 결과: **1 passed in 277.54s**.

처음에는 검토·계산 POST가 공통 30초 브라우저 제한 안에 응답하지 않아
브라우저 시험이 실패했다. 두 접수 요청에만 임시 180초 제한을 적용하고
대기 중 문구를 표시해 위 시험을 통과했다. 이는 접수 지연을 제품 수준으로
수용한 결과가 아니다. 서버의 근거·권한 검사는 그대로이며, 실제 부하에서
요청별 지연을 측정해 접수 응답 경로와 제한을 다시 정해야 한다.

이 시험은 실제 Codex CLI 실행, 독립 검토자, 농업 자료 G0, 제품 G1,
현장 G2, 작물·경제 전망 G3, 운영 G4의 증거가 아니다. 작성 폼에서 API를 거쳐
**신규** 검토 작업을 완료해 3D까지 처리하는 브라우저 시험은 당시에는
없었다. 등록은 서비스에서 수행했고 브라우저는 완료 검토 작업의
동일 키 재접수를 확인했다. 신규 검토·계산 연결은 아래 후속 확장에서 검증했다.
최초 완료 증명과 계산 후보를 후속 재조회에서 고정한 한계도 같다. 반복
권리/역할 감사가 길어지는 비용은 운영 성능 평가 대상으로 남긴다.

## 브라우저의 신규 계산 작업 접수·완료 확장 (2026-09-30)

같은 통합 시험에서 브라우저가 작성 농장·해제에 결합된 **신규** 계산 작업을
`POST /v1/authored-runs`로 접수했다. 시험 하네스는 화면에 표시된 새 작업 ID를
기준으로 실제 `AuthoredSimulationWorker`를 실행했고, 브라우저가 완료 상태를
다시 조회해 같은 저장 Run의 120시점 3D·그래프·표를 열었다. 검토 작업은 이미
완료된 작업을 동일 키로 재접수한 것이며, 별도 작업자의 비동기 완료를
브라우저 밖에서 시험했다. PostgreSQL 16.15/SCRAM과 실제 HTTPS 응답 8개,
Chromium 대조에서 **1 passed in 277.88s**였고 콘솔 오류는 0개였다.

이 확장도 처음 검증한 완료 증명과 계산 후보를 후속 조립에서 고정한다.
가짜 CLI, 합성 검토자 서명, 서버가 준비한 등록판본이므로 독립 G1이나
제품 환경의 사용자 작성·수집·검토 전체 경로는 여전히 보류한다.

## 브라우저의 신규 검토·계산 작업 전체 연결 (2026-09-30)

위 통합 시험을 수정해 브라우저가 등록 판본을 조회한 뒤 **새 검토 작업**도
`POST /v1/farm-authored-reviews`로 접수하도록 했다. 화면에 표시된 작업 ID를
기준으로 시험 하네스가 가짜 CLI를 실행하고, 실제 완료 검증기와 합성
관찰자·검토자 서명으로 별도 해제를 저장했다. 브라우저는 검토 완료를 다시
조회하고 새 계산 작업을 접수했다. 결정적 작업자가 Run을 원자 게시한 뒤
브라우저가 완료 상태와 120시점 3D·그래프·표를 읽었다.

격리된 PostgreSQL 16.15/SCRAM, 표준 HTTPS 응답 8개(검토/계산 접수는 각각
202), Chromium의 첫·끝 시각 및 표 값 대조에서 **1 passed in 244.15s**였다.
콘솔 오류는 0개였다. 같은 브라우저 스크립트의 기존 저장 Run 조회 경로는
별도 집중 시험이 다룬다. 서비스 준비 전에 비공개 아티팩트 디렉터리가
필요한 것을 첫 실행에서 확인해 시험 조립 순서를 수정했다.

등록 판본과 원천·경제 입력은 여전히 하네스가 사전에 준비한다. CLI는
`gpt-6-sol`이 아닌 직접 작성한 가짜 실행기이고, 실행 관찰자와 검토자 키도
시험 권한이다. 완성 증명과 계산 후보는 후속 API/작업자 조립에서 고정한다.
따라서 전체 G1, 실제 제품 CLI, 독립 해제·권리 재검사, 사용자 작성 화면,
G0/G2/G3/G4는 이 시험으로 통과하지 않는다.
