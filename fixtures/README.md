# Self-authored synthetic fixture inputs

The weather and economics v1 inputs are small algebraic sentinels for a future G1 software-contract trace. Thermal parameters v1 add proposed synthetic initial, facility, control, conversion, and numerical inputs; [manifest v2](manifest-v2.json) pins all three raw files. These are self-authored, not provider observations, farm records, crop outputs, commercial prices, or measured greenhouse coefficients. The manifest's `synthetic_input_review_id` is an author declaration for later server verification. It is not an external-source G0 approval or an accepted thermal Run. The current generic G0 evaluator holds synthetic records. A deterministic thermal engine and actual G1 result checks are later tasks.

The weather file has adjacent UTC `[start_utc,end_utc)` intervals. `T_o` is kelvin, `phi_o` is a dimensionless fraction, and `p_o` is pascal. `solar_interval_energy` is the **total J/m² over that interval**; the zero is explicit. There is no gap fill. In `Asia/Seoul` on 2026-10-15, the first interval converts from 08:00–09:00 UTC to **17:00–18:00 KST** and has positive interval energy; the second converts from 09:00–10:00 UTC to **18:00–19:00 KST** and has explicit zero energy. Both are algebraic sentinels. Neither value claims astronomical consistency or local weather. A later engine must derive `w_o` with a registered saturation-pressure law, divide interval energy by duration for incident W/m², then use separately sourced area and absorbed fraction for aggregate solar W. This fixture supplies neither result nor a passing trace. The thermal input and trace requirements are in [thermal-v1](../contracts/thermal-v1.md).

This fixture package defines **INPUT only**. The final thermal trace requires `source_records[*]` and `synthetic_input_review_id`; the parameter fixture supplies neither a completed source-record array nor an accepted trace. Its `input_records` are immutable file-ID and JSON-pointer plans, not server-issued source records. A future deterministic adapter and server must resolve those IDs through manifest raw hashes for each interval and variable, preserve exact original units and hypothetical applicability times, calculate the derived fields with versioned rules, and create field-level source records. They must check the author and synthetic label, provider QC (`not_applicable` for self-authored inputs where appropriate), project QC, reviewer, and self-owned use/display/redistribution rights. The NWS formula source has a separate public-domain disclaimer and a completed independent CLI source and conditional-rights review bound to the former fixture and manifest bytes; [the source ledger](../contracts/thermal-sources.md) records its scope and limits. The server must independently verify all links before any G1 software-contract trace can be accepted. Author self-review and the separate CLI review establish neither an actual G0 pass nor field accuracy.

## Thermal parameter v1 and preregistered checks

[Thermal parameters v1](synthetic-thermal-parameters-v1.json) explicitly mark the rounded gas, heat, facility, initial-state, flow, heater, and zero-ground values as self-authored assumptions. Its registered [NWS formula PDF](https://www.weather.gov/media/epz/wxcalc/vaporPressure.pdf) states `e_s(hPa)=6.11*10^(7.5*t_C/(237.3+t_C))`. The fixture registers the exact project transcription and SHA-256, NWS coefficients, and the project's inclusive 289–293 K software-test range. For SI conversions, [BIPM SI Brochure Appendix 2, MeP-K, PDF p. 2](https://www.bipm.org/documents/20126/41489682/SI-App2-kelvin.pdf/) supports `kelvin_to_celsius_offset=273.15 K` in `t_C=T_K−273.15`, and the [BIPM SI prefix table](https://www.bipm.org/en/measurement-units/si-prefixes) supports `hpa_to_pa_factor=100 Pa/hPa` from hecto=`10²`. The fixture maps each coefficient to its exact URL under `unit_basis.source_urls`; `bipm-si-unit-conversions` and `bipm-si-conversion-transcription-v1` are project-local IDs, not BIPM publication metadata. The NWS PDF does not state a formal validity range, quantitative accuracy, exact publication date, or dated provider version. Its saved 72,617 bytes have SHA-256 `74e5a28ee21bde51d5ffad17f2418dc5c827c338d1bc11a09cbd7c623b87b621`; the PDF is kept outside this repository. The independent CLI review hashed that saved copy but did not compare it with a fresh remote download. The [NWS disclaimer](https://www.weather.gov/disclaimer) permits lawful public-domain use with non-endorsement, no claim of NWS content as one's own, and no modified information presented as official, subject to a third-party caveat. It states no general attribution requirement; the project may voluntarily credit NWS. No special notice appeared in the PDF's extracted text. The independent CLI review of these conditions was not human rights approval or a server gate decision. Apache-2.0 applies to the self-authored fixture and formula implementation, not to relicensing the source PDFs or pages.

Each proposed thermal hour refers to the weather v1 fixture and its exact interval and field-level record IDs. It does not recopy raw weather values. Versioned `thermal-outdoor-w-v1` applies the Kelvin/Celsius and hPa/Pa conversions before deriving outdoor humidity ratio from linked temperature, RH, pressure, rounded gas constants, and the NWS equation; its input IDs include the saturation rule. `thermal-solar-interval-v1` converts the linked interval solar total using floor area, absorbed fraction, and the 3,600 s interval duration. The resulting power is held only within its hour. Both hours tile into 60 positive 60 s steps. The parameter fixture preregisters absolute residual and 60-versus-two-30 s limits with units, rationale, and versions before the engine exists. [The source ledger](../contracts/thermal-sources.md) records the NWS-recomputed invariant-envelope derivation, binary64 operand-sum assumptions, and holds. These are software contract checks, not measured accuracy or an engine run.

The economics file uses exact decimal strings for all quantity and money inputs. Dispatch, delivery, inspection, and recognition occur on one Asia/Seoul day; later collection and cost payments have distinct dates. Only recognized `S` earns conditional revenue. ## Byte pins and IDs

- The canonical content ID for each input is `sha256:` followed by the lowercase SHA-256 of its **complete raw UTF-8 file bytes**, including indentation and final newline. `byte_length` counts the same bytes. The manifest binds repo-relative paths to those IDs, not to parsed or reserialized JSON. JSON values never contain their own raw hash.
- `fixture_id` and `manifest_id` are semantic version labels. `vintage_id` and `revision_id` identify this authored release. A changed byte requires a new fixture revision and manifest; do not silently replace a pinned release. The manifest cannot contain its own raw hash without a cycle. A consumer may compute its content ID as `sha256:<SHA-256 of complete raw manifest bytes>` and pin that in an external immutable run record.
- In manifest file rows, `source_locator` is the local fixture path and `product_id` is the fixture ID. Neither is a third-party source URL. The separate NWS law record carries the official final PDF URL, exact raw PDF hash and byte count, retrieval time, and HTTP Last-Modified distinct from unknown publication/availability times. Manifest authoring/publication/availability/retrieval times are before the economics `decision_at_utc`. Manifest v2 labels the future weather hours as **hypothetical applicability**, with null observation times; economic event dates are conditional assumptions. Rights for the self-authored files are access, store, transform, display, and redistribute under the repository's [Apache-2.0 license](../LICENSE). That license does not cover the NWS PDF. The self-check and reviewer fields are author declarations for software tests, not server gate evidence.
